# Lyzr research and takeaways for our local agent platform

Researched 10 October 2026. This is an evolving product and architecture analysis,
not a final version specification. The user wants both the conversational/research
experience and the autonomous tool execution that inspired them in Grok. Their
existing requests are examples of the platform's potential, not a ceiling on it.

## Main recommendation

Build a local agent workspace with a strong conversational front door and a durable
execution engine behind it. Borrow Lyzr's separation of builder, runtime, knowledge,
memory, workflows, evaluation and control. Keep these modules usable through the
same interfaces from the CLI, a future web interface, and other local applications.

Lyzr's most valuable idea is the full lifecycle: describe an objective, configure
capabilities, execute with evidence, measure results, inspect failures, and improve
the configuration. Our current platform supplies an early runtime and registry;
the next work should connect those foundations into a coherent everyday experience.

## Research scope and confidence

I retrieved official product pages, more than forty documentation pages, and public
files from Cognis, OpenGAP and GitAgent. The source catalog records 76 unique page
and code-file URLs, 72 successful responses and four failed documentation paths.
Repository README, license and package metadata checks are recorded separately.

The research covers publicly documented behavior and selected implementation files.
I did not log into Agent Studio, buy a plan, run a commercial deployment, install
these third-party runtimes, or benchmark Lyzr. Documentation is evidence of what
Lyzr describes, not independent proof of every production guarantee.

Important access and documentation limits:

- The public pricing response requested JavaScript/cookies; current prices were
  not established. Studio and Architect returned application shells, so their
  authenticated interfaces were not inspected.
- Four Architect paths in `llms.txt` returned 404. The actual Architect introduction
  was found through navigation and read successfully.
- Some documentation summaries differ from detailed pages. For example, the RAG
  concept page broadly lists Snowflake, but the Semantic Model setup page marks
  Snowflake as coming soon. The detailed Global Context page describes explicit
  attachment, whereas the concept page calls it organization-wide context.
- The Sovereign AI page distinguishes live software from forthcoming models and a
  hardware appliance. These are not all demonstrated shipped capabilities.
- Claims such as 99% verification accuracy, customer savings and automatic
  improvement were not independently verified. They are not targets we can inherit
  merely by following the same architecture.

## 1. Understand the product as a set of layers

Lyzr's current architecture documentation describes five layers: Agent Framework,
Agent Studio, Architect, model providers, and infrastructure. The first three are
the runtime, builder and application layers; the final two supply models and hosting.

| Lyzr component | Publicly described responsibility | Takeaway for us |
| --- | --- | --- |
| Agent Framework | Inference, tools, memory, knowledge, policy hooks and protocol adapters | Keep one execution engine behind all interfaces |
| Agent Studio | Agent configuration, playground, knowledge, workflows, evaluation and governance | A local interface should expose the existing registry rather than duplicate it |
| Architect | Generate applications from natural-language intent, wiring agents into a complete application | Start with conversational agent/workflow creation; full application generation is a later subsystem |
| Manager Agent | Select workers, delegate, chain work and synthesize answers | Upgrade our one-specialist router into bounded planning and delegation |
| SuperFlow | Deterministic workflow graph with durable steps, waits, retries and history | Known processes need an execution state machine, not repeated model improvisation |
| Cognis | Cross-session memory, extraction, updates and retrieval | Conversation logs need a deliberate retrieval and correction layer |
| Knowledge services | Document retrieval, relationship graphs and structured-data querying | Give each kind of information an appropriate retrieval interface |
| Evaluation/Improvement Engine | Simulate cases, examine traces, propose configuration improvements | Model quality needs its own tests and versioned feedback loop |
| OpenController | Discover, observe and enforce operational policy across agent deployments | Put controls in the actual model/tool execution path |
| Blueprints/skills | Reusable agents and capability packages | Reuse configurations and procedures without specialist branches in the core |

Source: [architecture](https://docs.lyzr.ai/enterprise/get-started/architecture),
[Blocks](https://docs.lyzr.ai/enterprise/lyzr-blocks/overview),
[OpenController](https://www.lyzr.ai/opencontroller/).

## 2. Make the conversational experience a first-class interface

Lyzr documents persistent sessions, normal chat endpoints, server-sent-event
streaming, multimodal chat, and a playground for messages and attachments. Its
Conversational Builder turns a description into an editable configuration and asks
questions about tools, knowledge and behavior before generating a draft.

For our system, the natural interface should let the user:

- Continue a conversation and have the relevant project context carried forward.
- Attach documents, receive cited answers, and inspect the underlying evidence.
- Say “create an agent that researches competitors” and receive a validated draft
  showing its purpose, model, tools, memory scope and example tests.
- See progress and artifacts during a task, interrupt it, and continue from a saved
  state rather than having to restart a long command.
- Ask how a result was obtained and see the plan, source references, tool receipts
  and validation results. These are operational evidence, not hidden model thoughts.

Our existing adapter sends `stream=False`; the CLI creates independent tasks.
Adding a web chat without session and event APIs would leave the experience shallow.
The first interface should therefore share the same task engine and explicit event
stream used by the CLI. Browser errors, reconnects and duplicate submissions must
not silently launch duplicate jobs.

Sources: [agents and endpoints](https://docs.lyzr.ai/enterprise/get-started/concepts/agents),
[Conversational Builder](https://docs.lyzr.ai/enterprise/agent-studio/agents/conversational-builder),
[Studio Builder](https://docs.lyzr.ai/enterprise/agent-studio/agents/studio).

## 3. Use dynamic planning and deterministic workflows together

Lyzr distinguishes two useful execution modes. The Manager decides what workers
are needed based on the request. SuperFlow runs a defined graph when the process is
already known. A conversational Manager can start a deterministic workflow and
present its result afterward.

Our Manager currently returns exactly one `agent_id` and one capability reason.
The selected specialist then runs a bounded tool loop. This is dynamic routing,
but it is not multi-agent planning or a coordinated team.

The proposed extension is a typed plan containing steps, dependencies, assigned
capabilities, input references, expected output contracts and verification checks.
Validate the graph before execution. Reject nonexistent agents, dependency cycles,
unavailable tools and assignments beyond the granted scope. Workers receive the
specific information they need, rather than every other worker's entire history.

Keep the Manager focused on coordination. Lyzr's detailed guide recommends leaving
domain knowledge and direct tools with workers. That is a useful default for our
small-model environment: the coordinator plans, workers act, and validators check.

On the Dell, a team of ten configured agents need not mean ten loaded models or ten
simultaneous inference jobs. Use the existing inference lock and initially execute
model work sequentially. Parallelize retrieval or independent I/O only when useful.

Sources: [orchestration concepts](https://docs.lyzr.ai/enterprise/get-started/concepts/multi-agent-orchestration),
[Manager setup](https://docs.lyzr.ai/enterprise/agent-studio/manageragent/studio),
[SuperFlow](https://docs.lyzr.ai/enterprise/agent-studio/superflow/overview).

## 4. Durability is more than recording a completed task

SuperFlow documents per-step journals, recovery after restart, persisted retries,
approval waits, pause/resume/termination, scheduled triggers and replay. These are
directly relevant to an assistant that works while the user is doing something else.

Our SQLite event tables record messages, calls and outcomes, but they do not yet
form a resumable job queue. A crash can leave a task marked `running`; no worker
lease, checkpoint recovery or resume command restores the execution position.

Add durable job and step records, explicit state transitions, attempt numbers,
worker leases, cancellation requests and output references. Do not keep a model
loaded or an HTTP request alive while waiting for a future timer or a human decision.

Lyzr describes “exactly-once” side effects. We should implement a narrower guarantee
we can test. Consider an email API accepting a send, followed by a crash before our
completion record is written. A local journal cannot tell whether the remote action
occurred. Retrying blindly could send twice. External writes need provider-supported
idempotency keys, transaction/outbox patterns where applicable, or an explicit
reconciliation state when the outcome is unknown. Replaying evidence and re-running
a side effect must be separate operations.

Source: [SuperFlow reliability](https://docs.lyzr.ai/enterprise/agent-studio/superflow/reliability).

## 5. Separate session memory, lasting memory, knowledge and shared instructions

Lyzr explicitly distinguishes recent conversation history, cross-session memory,
Global Context and knowledge bases. Cognis adds fact extraction, updates, temporal
handling and hybrid retrieval. These distinctions prevent an unbounded transcript
from becoming the agent's only source of context.

| Information | Proposed location and retrieval | Example |
| --- | --- | --- |
| Conversation | Session messages with a bounded recent window | The clarification from the last turn |
| Project state | Project/task artifacts and decisions | Current campaign draft and unfinished research |
| Lasting preference | Scoped, editable memory with provenance | Preferred tone or a recurring business objective |
| Source knowledge | Indexed documents with citations and permissions | A handbook section or product specification |
| Shared instructions | Versioned context explicitly attached to agents/projects | Brand voice or terminology |
| Action history | Structured execution receipts | A report was saved at a particular path |

Our database preserves history, but TaskService does not retrieve earlier tasks
into a new conversation. `settings` and `parent_id` fields are configuration
metadata; their presence does not implement memory or delegation.

Build scope into the memory key: owner, project, agent and session. Store source
references and timestamps. A correction should supersede an old fact visibly.
Support viewing, editing, forgetting and retention settings. A quoted document or
an untrusted website must not become a durable user preference automatically.

Start with SQLite and full-text retrieval for a small local corpus. Add local
embeddings through a provider interface after retrieval and resource measurements
justify them. Advanced hybrid ranking is useful, but fixed ranking weights from a
vendor benchmark need evaluation on our own data.

Sources: [memory concepts](https://docs.lyzr.ai/enterprise/get-started/concepts/memory-context),
[Global Context](https://docs.lyzr.ai/enterprise/agent-studio/agent%20features/global%20context),
[Cognis repository](https://github.com/Lyzr-Cognis/cognis).

## 6. Cognis is worth studying, but is not a drop-in offline solution

The public Python package has an MIT license and local Qdrant plus SQLite storage.
Its README distinguishes local and hosted clients. The examined package manifest
declares four runtime dependencies, including LiteLLM and qdrant-client.

Selected implementation details matter:

- The configuration defaults to a Gemini embedding model and `gpt-4.1-mini` for
  extraction. The examined embedding implementation requires a Gemini/Google key.
  Text can therefore leave the machine in the default “local” configuration.
- Local and hosted memory use explicit owner/agent/session scoping. This interface
  is a useful pattern even if we implement our own storage first.
- Extraction supports add, update, contradiction and delete operations. Retaining
  conflicting evidence is more useful than silently overwriting a fact.
- The examined embedding cache keys on the first 200 characters. Different long
  inputs with the same prefix can share a key. Our cache should hash the entire
  normalized input plus model/configuration identity.

Recommendation: adopt the separation of storage, extraction, embeddings and search.
Evaluate Cognis behind a `MemoryProvider` interface later; first establish genuine
local endpoints, full-input cache keys, deletion behavior and isolation tests. No
Cognis package was installed as part of this research.

Sources: [README](https://github.com/Lyzr-Cognis/cognis/blob/main/README.md),
[configuration](https://github.com/Lyzr-Cognis/cognis/blob/main/cognis/config.py),
[embedding implementation](https://github.com/Lyzr-Cognis/cognis/blob/main/cognis/embeddings/gemini.py),
[manifest](https://github.com/Lyzr-Cognis/cognis/blob/main/pyproject.toml).

## 7. Ground answers in evidence through the right knowledge interface

Lyzr documents three knowledge options: a document KB, a knowledge graph and a
semantic model for structured data. The document KB exposes chunking, retrieval
limits, thresholds, basic similarity, MMR and HyDE, and a retrieval playground.
It also distinguishes a simple retrieval pass from iterative agentic retrieval.

Our document tool currently extracts a bounded amount of whole-file text. That is
useful for small CVs and reports, but it is not an indexed knowledge base. Whole-file
injection becomes expensive as the corpus grows.

For our first KB, retain file/page/section provenance, source hashes and ingestion
times. Test retrieval separately from answer generation. Return answer citations
that resolve to actual retrieved content. Support “the supplied sources do not
answer this” and source conflicts. Changed documents should invalidate their old
chunks; retrieval must respect project and user access before returning text.

For web research, save public source URLs, fetch times and extracts behind the same
evidence contract. The model's remembered facts are not a substitute for live
research. Limit fetches and redirects, treat page content as untrusted, and record
when a page could not be accessed.

Structured data should initially use reviewed read-only query interfaces with table
allowlists and row limits. A knowledge graph becomes useful when measured questions
require relationships across sources; it is not a prerequisite for document Q&A.

Sources: [RAG concepts](https://docs.lyzr.ai/enterprise/get-started/concepts/rag-knowledge),
[KB controls](https://docs.lyzr.ai/enterprise/agent-studio/knowledgebase/studiokb),
[semantic model](https://docs.lyzr.ai/enterprise/agent-studio/knowledgebase/studiosem),
[knowledge graph](https://www.lyzr.ai/knowledge-graph-as-a-service/).

## 8. Grow tools through contracts and adapters

Lyzr supports custom function/OpenAPI tools, prebuilt connectors, MCP and A2A.
It documents shared credentials and per-user credentials as distinct deployment
choices. MCP is a tool interface; A2A is an agent delegation interface.

For us, each tool needs a typed input/output contract, action category, scope,
timeout, credential reference, provenance and retry/idempotency behavior. A
connector should offer separate read, draft and external-write actions. An agent
receives only explicitly assigned actions.

This differs from Lyzr's prebuilt-tool page, which says all connector actions are
enabled by default unless deselected. We should retain our existing explicit tool
assignment default as connectors become more powerful.

Do not infer that adding a connector is the same as adding a safe generic shell.
Executing repository code or downloaded skill scripts needs an actual sandbox and
resource limits. The current user-only trusted pytest command is not a sandbox.

For local MCP, allow local transports rather than inheriting the SaaS documentation's
requirement that a server be publicly reachable. A2A can later connect the Dell to
other trusted machines or agents without forcing every agent into one framework.

Sources: [tool concepts](https://docs.lyzr.ai/enterprise/get-started/concepts/tool-calling),
[prebuilt actions](https://docs.lyzr.ai/enterprise/agent-studio/tools/pre-built),
[MCP](https://docs.lyzr.ai/enterprise/integrations/mcp),
[A2A](https://docs.lyzr.ai/enterprise/integrations/a2a-protocol).

## 9. Make controls part of execution

OpenController's useful principle is enforcement in the request path. A dashboard
that merely reports an action afterward cannot stop it. Lyzr also documents input
and output guardrail hooks and explicit organization roles.

Our executor already checks enabled tools, assignment, permission level and scoped
paths. Extend that foundation with task-wide token/time/tool budgets, cancellation,
connector scopes, approved destinations and exact proposed external actions.
Recheck permission at execution time, not only when creating a plan.

Approval behavior must respect the user's existing authorization. Read-only work
and reversible local preparation should progress automatically within granted
scope. When a consequential external action needs approval, present its concrete
recipient, content, destination, cost and artifact first. Store the decision and
bind it to that action; editing the action must invalidate the old approval.

For an initial single-user local app, do not build enterprise SSO before useful
workflows. Add resource ownership and scope fields now, and introduce multi-user
roles when multiple users actually share it. Existing SQLite events are a debugging
history, not an immutable compliance log or certification.

Sources: [OpenController](https://www.lyzr.ai/opencontroller/),
[Responsible AI](https://docs.lyzr.ai/enterprise/agent-studio/responsible-safe-ai/Responsible),
[roles](https://docs.lyzr.ai/enterprise/agent-studio/governance/roles-permissions),
[audit log](https://docs.lyzr.ai/enterprise/agent-studio/governance/audit-log).

## 10. Evaluate execution, answer quality and business outcomes separately

Lyzr's evaluation and simulation pages describe scenarios, personas, generated or
manual cases, tool correctness, faithfulness and task completion. Its Improvement
Engine links issues to traces, suggests prompt/configuration changes with a diff,
records versions and limits evaluation resource use.

Our 58 automated tests verify engineering behavior. They do not establish that an
LLM produces correct results on unseen tasks. Actual inference already exposed
1.7B routing mistakes, a coding-quality failure and 4B tool timeouts. Those failures
should become permanent evaluation examples, not disappear behind a passing suite.

Build a small, versioned corpus of real workflows with objective checks:

- Routing: include ambiguous prompts and test newly registered agents.
- Tools: exact tool, arguments, scope and actual receipt.
- Recruitment: every claim linked to candidate/job evidence; missing evidence
  stays missing; the report is an assessment rather than an automated hiring decision.
- Code: execute meaningful cases in a sandbox, including non-adjacent duplicates
  for the earlier failed deduplication example.
- Knowledge: correct cited passage, insufficient evidence, stale sources and
  conflicting documents.
- Workflows: recover after restart and prevent duplicate externally visible actions.

Keep generated training scenarios separate from held-out evaluation cases.
Model-judge scores can help triage, but a model grading its own plausible answer is
not sufficient evidence of correctness. Track objective pass rate, p50/p95 latency,
tokens, model loads, queue time and human correction rate.

Marketing outcomes such as bookings or campaign return need connected real data.
Generating a campaign document is an artifact success; it is not measured revenue.

Sources: [evaluation concepts](https://docs.lyzr.ai/enterprise/get-started/concepts/evaluating-agents),
[simulation](https://docs.lyzr.ai/enterprise/agent-studio/agent%20eval/agentsimulation),
[Improvement Engine](https://docs.lyzr.ai/enterprise/agent-studio/agent%20eval/improvement-engine),
[tracing](https://docs.lyzr.ai/enterprise/agent-studio/agent%20eval/tracing).

## 11. Keep agent definitions portable and changes reversible

OpenGAP defines agents through files such as `agent.yaml`, `SOUL.md`, `RULES.md`,
skills and workflows. GitAgent is a separate runtime implementation. Public
licenses examined for OpenGAP, GitAgent and Cognis were MIT. Their current package
manifests identify OpenGAP 0.5.0 and GitAgent 2.2.0; the GitAgent marketing page's
v0.3.0 label is not the current repository package version.

The relevant pattern is configuration as a portable artifact, with versioning,
diffs and rollback. We already accept JSON agent definitions; we can add a
versioned export bundle without replacing SQLite as runtime storage. A run should
pin the complete configuration version so edits made during execution do not
silently alter its meaning.

Commit reviewed prompts, skills and workflow definitions. Keep private transcripts,
raw user memory, secrets and generated runtime state out of shared Git repositories.
File-based memory is not a reason to publish someone's conversation history.

A skill package can describe a procedure and required capabilities. It must not
grant itself more permissions by including a script. Pin versions/digests rather
than automatically refreshing an executable dependency for every agent.

Sources: [OpenGAP](https://github.com/open-gitagent/gitagent-protocol),
[GitAgent](https://github.com/open-gitagent/gitagent),
[Studio versioning](https://docs.lyzr.ai/enterprise/agent-studio/control-plane/version-control),
[skills](https://docs.lyzr.ai/enterprise/agent-studio/connect/skills).

## 12. Define improvement honestly

Lyzr describes configuration hardening; its GitAgent marketing also uses
“reinforcement learning” language. The selected public `reinforcement.ts` file
updates skill usage statistics, heuristic confidence and negative examples in
SKILL.md. That file does not demonstrate LLM weight training. This is a useful
feedback mechanism, but its confidence value is not a calibrated probability.

For our system, improvement should initially mean: retain corrections, identify
repeated failures, propose a versioned prompt/skill/model change, evaluate it on
held-out cases, and activate or roll back according to the configured policy.
Expose exactly what changed and which metric improved. Weight fine-tuning is a
separate future capability requiring data, compute and validation.

The examined GitAgent sandbox adapter uses an E2B provider through an optional
dependency. It does not establish a local Windows sandbox. Borrowing its tool loop
or installing its runtime would not by itself satisfy our local execution goal.

Sources: [skill feedback implementation](https://github.com/open-gitagent/gitagent/blob/main/src/learning/reinforcement.ts),
[sandbox adapter](https://github.com/open-gitagent/gitagent/blob/main/src/sandbox.ts).

## 13. Package complete workflows as reusable blueprints

Lyzr's Blueprints include role, goal, instructions, recommended model, tools,
knowledge expectations and sample tests. Its Agentic OS pages organize specialists
around function-level objectives: Skott for marketing, Jazon for sales, Diane for
HR and Jeff for support. The useful abstraction is a coordinated workflow with
measurable outcomes, not the product names or the number of agents advertised.

For our platform, build a few complete blueprints through the generic interfaces:

| Blueprint | Prepared artifacts | Measurement once relevant data exists |
| --- | --- | --- |
| Restaurant marketing | Research notes, campaign brief, content calendar, ad drafts and tracking plan | Qualified bookings/leads and verified campaign results |
| Recruitment preparation | Evidence-linked assessment, skill gaps, interview questions and practical-test draft | Reviewer corrections and time saved; human hiring judgment |
| Developer change | Reproduction, patch proposal, sandboxed checks and review report | Verified behavior and regression outcomes |
| Research/SEO | Sources, competitor comparison, technical findings and prioritized actions | Citation correctness, issue resolution and later traffic data |
| Support knowledge | Answer with citations, escalation packet and KB update draft | Verified resolution and reviewer acceptance |

The same system should accept a future specialist unrelated to these examples.
Blueprints remain editable configurations with tests, rather than new branches
inside TaskService.

Sources: [Blueprints](https://docs.lyzr.ai/enterprise/agent-studio/orchestration/blueprints),
[Agentic OS](https://www.lyzr.ai/agentic-os/),
[Skott](https://www.lyzr.ai/skott/), [Jazon](https://www.lyzr.ai/jazon/),
[Diane](https://www.lyzr.ai/diane/), [Jeff](https://www.lyzr.ai/jeff/).

## 14. Preserve room for voice, proactive work and larger deployments

Lyzr documents scheduled agent inputs, signed webhooks, retries and execution
history. Its voice layer separates realtime audio models from a configurable
speech-to-text → model → text-to-speech pipeline.

For us, a local voice pipeline can later feed the same session and task APIs as
chat. Start with push-to-talk and measured latency before promising continuous,
interruptible voice. Local OCR and vision should likewise be optional services,
not dependencies for ordinary text work.

Proactive work should come from explicit recurring objectives and triggers: a
weekly competitor briefing, a report on changed files, or a reminder about an
unfinished project. Configure timezone, overlap rules, missed-run handling,
budgets and the permitted action scope. The user is in Asia/Calcutta; a “9 AM”
schedule should not silently use the cloud host's UTC timezone.

Distributed execution and additional machines remain possible through worker and
provider interfaces. They should follow actual hardware validation, not assumptions
about the Dell or HP. No third-party appliance or cloud plan is required for the
recommended local roadmap.

Sources: [scheduler](https://docs.lyzr.ai/enterprise/agent-studio/automation/scheduler),
[webhooks](https://docs.lyzr.ai/enterprise/agent-studio/automation/webhook-trigger),
[voice](https://docs.lyzr.ai/enterprise/agent-studio/voice/overview),
[sovereign stack](https://www.lyzr.ai/sovereign-ai/).

## 15. Current gaps and recommended order

| Capability | Our current state | Recommended next step |
| --- | --- | --- |
| Configurable specialists | Implemented and tested | Preserve generic registration; add revisions and export |
| Model independence | Ollama and OpenAI-compatible adapters | Evaluate profiles on real tasks before auto-selection |
| Conversation | Independent CLI requests | Sessions, local API, streamed events and local chat interface |
| Memory | Stored messages; no cross-task retrieval | Scoped, editable session/project memory |
| Knowledge | Bounded document reads | Indexed retrieval, provenance and cited answers |
| Research | No built-in public-web research tool | Bounded fetch/search provider with source receipts |
| Coordination | One specialist selected per request | Typed multi-step plans and worker handoffs |
| Workflow durability | Persisted logs; no resume engine | Queue, step journal, leases and recovery |
| Tools | Scoped local files/docs and read-only Git | Typed connector adapters and per-action permissions |
| Quality | 58 engineering tests plus limited real-model probes | Held-out model/workflow evaluation corpus |
| Operations | Task JSON and timing events | Inspectable timeline, queue metrics, budgets and cancellation |
| Agent builder | JSON/CLI registration | Conversational drafts plus editable forms and validation |
| Reuse | Starter agents and configuration examples | Skills and complete tested workflow blueprints |
| Improvement | No implemented feedback loop | Correction capture, proposed diffs, evaluation and rollback |
| Automation | No scheduler/webhook service | Durable timers and authenticated event triggers |
| Voice/vision | Not implemented | Optional adapters after text workflow and hardware validation |

The proposed sequence is in [the evolving roadmap](../../roadmap/2026-10-10-evolving-platform.md).
Its milestones are independently useful, while their interfaces leave the larger
vision open. This research did not implement those future capabilities or change
the working platform's behavior.
